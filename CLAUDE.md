# Project Ledung — notes for Claude sessions

Ledung runs several Claude Code sessions and shows them in one web page. You may well be running inside it: Ledung can be developed from a Ledung session. Read [docs/brief.md](docs/brief.md) for the goal and the plan, [docs/decisions.md](docs/decisions.md) for decisions made since, and [docs/steps/](docs/steps/) for the current step. Open work is on the GitHub board (https://github.com/orgs/Fluffy-Fluffy-and-Bouncy/projects/1), as issues with one milestone per step. **New issues are filed on the public `Fluffy-Fluffy-and-Bouncy/ledung`** (since 2026-11-02), and the open issues were moved there that day, each with a "Moved from Project-Ledung#N" line; the old issue is closed with a "Moved to" link, so follow it from an old number. The private `Fluffy-Fluffy-and-Bouncy/Project-Ledung` keeps history and the issues that stayed (Testing cards, #464, #465, #451, #455, #456, #459, #461, #463), referred to as `Fluffy-Fluffy-and-Bouncy/Project-Ledung#N`.

Personal preferences and machine details, if any, are in `CLAUDE.local.md` next to this file (not committed).

## Working on the project

- **Decisions are recorded** in `docs/decisions.md` with their date. Issues waiting on a decision carry the `decision-needed` label.
- **Every PR that changes what Ledung does writes its bullet(s) in `docs/changes/<issue>.md`, and never edits a changelog** (issue #417, since 2026-11-19), in the format [docs/changes/README.md](docs/changes/README.md) gives. `npm run publish:dev` folds the waiting files into [CHANGELOG-dev.md](CHANGELOG-dev.md) under the new dev version, `npm run publish:public` into [CHANGELOG.md](CHANGELOG.md) under the new public release, and each pushes that to main. The pre-push hook refuses a push that changes `src/`, `web/` (not `web/dist/`) or `scripts/` without a new `- ` line in `docs/changes/`; a commit trailer `Changelog: none` is for changes with nothing user-facing (tests, refactors), and a reviewer checks it is honest. This is for every contributor and every manager, FFBuddha's included.
- **Keep the repository generic.** Nothing about a particular work project (people, tickets, compliance rules, container names) goes in the repository; it belongs in `ledung.config.local.json`, which is not committed.
- **Screenshots are taken in dark mode**, not light mode; add a light one only when the change is about light mode itself (Martin, 2026-10-20: "When we take screenshots, take them in dark mode, not lightmode.").
- **Dark is the designed theme; light is basic** (Simon, 2026-11-17, #345): a new colour needs a designed dark value and a light value that is readable; light mode isn't tested or screenshotted unless a bug is reported.
- **Ledung is independent of the projects it runs.** Don't use, inspect or design around the user's other projects when working on Ledung; develop and test with throwaway projects and containers, so Ledung works in any environment.

## Running Ledung without breaking the one you are in

- Ledung runs from a release copy in the user data folder (`%APPDATA%\Ledung\app\<timestamp>` on Windows; see [docs/development.md](docs/development.md#running-ledung-from-a-clone)), never from this folder. **Never edit files in the user data folder**; change the source here and run `npm run release`.
- A release is picked up when the person using Ledung presses **Restart Ledung**. Sessions survive the restart (each runs in a session host, `src/host/`), so a release never cuts you off. Don't restart or stop Ledung yourself.
- **Never stop processes broadly.** Ledung, its launcher and every session host are `node` processes; `claude` processes include your own. When cleaning up after a test, stop the test Ledung by the process listening on its port, and its hosts by their command line, which contains the test's data folder. A test Ledung's own command line does not contain that folder (it is in the environment), so a filter on the folder name misses it.
- To try Ledung for real, start a throwaway copy with its own config, data and port, so it doesn't touch the real one:
  `LEDUNG_CONFIG=<temp>/config.json LEDUNG_DATA_DIR=<temp>/data node src/main.ts --no-open` (port set in that config, e.g. 4396). Read the sign-in token from `<temp>/data/auth-token`; API calls need the `ledung_auth` cookie and, for changes, an `Origin` of `http://127.0.0.1:<port>`. Use Haiku for test sessions.

### Play-checking the desktop app and Ledung's features

A play check tries a merged change the way a person would, in throwaways only. Try these tools before calling a step out of reach. Each line says what the tool reaches and where it stops (from the agent play checks of 2026-11-22 on #428, #454, #360, #485 and #490). Never use the real Ledung, its app, its data, its Start menu entry, its relay or its link.

- **Driving the desktop app:** playwright-core's Electron driver (`_electron.launch` on `desktop/main.ts`, with the throwaway's `LEDUNG_CONFIG` and `LEDUNG_DATA_DIR`, so the app's Electron profile is in the throwaway data folder) reads and drives both the page and the main process. playwright-core is not a dependency; pass its path in, as `test/loopback/*.ts` do with `PLAYWRIGHT`. **Its focus emulation makes every page report `document.hasFocus()` true**, so Ledung's rule "notify only when hidden or unfocused" never fires. Turn the emulation off first with the DevTools call `Emulation.setFocusEmulationEnabled` `{ enabled: false }`. Playwright's key events and Electron's `sendInputEvent` don't reach the app menu (⌘N does nothing). A system key event sent to the app's process does reach it (macOS `CGEventPostToPid`). A made app (see below) can be started with `--remote-debugging-port=0`, plus `--inspect=0` for the main process, and read over those ports instead.
- **Process and window names:** on macOS, `osascript` with System Events gives a process's displayed name, `lsappinfo` gives the name LaunchServices uses, and the CoreGraphics window list gives each window's owner, title and id. Read what the menu bar, Dock and ⌘-Tab show from the app's `Info.plist`. A session usually has no Accessibility permission (System Events fails with `-1719`), so it can't click, type or read menu items: drive through the app's debugging ports instead. On Windows, read a window's `MainWindowTitle` and `IsWindowVisible`, send `WM_CLOSE` to do what ✕ does, and read taskbar names through UI Automation.
- **Screenshots:** capture the app's window only, never the whole screen, which shows the person's other windows. Use Electron's `webContents.capturePage()` or Playwright, `screencapture -l <window id>` on macOS (the id comes from the window list) or PrintWindow on Windows. Take them in dark mode. `gh` can't attach images from the command line, so keep them in the worktree's `review-evidence/<check>/` and name them in the comment.
- **Two linked computers:** `test/loopback/linked-pair.ts` starts two throwaway Ledungs behind a local relay (`relay/relay.ts`, loopback only), with self-signed certificates for `*.l.test`. Link them the way Settings → Linked computers does. A browser or the app reaches them when `*.l.test` is mapped to the relay's loopback front (Chromium `--host-resolver-rules=MAP *.l.test:443 127.0.0.1:<front>`). Never use the real relay, a real link code or a real computer's tab. This doesn't reach two physical computers.
- **Passkey pages:** a DevTools virtual authenticator in a Chromium page: `WebAuthn.enable`, then `WebAuthn.addVirtualAuthenticator` (ctap2, internal, resident key, user verification, automatic presence), as `docs/steps/computer-tabs-link-loopback/link-pairing.ts` does. `test/fake-passkey.ts` builds the same bytes for code tests. Together they reach enrolling and signing in with a passkey. They don't reach a phone, Face ID or a physical key.
- **A notification to raise:** in a throwaway project with `"permissionMode": "default"`, tell a Haiku session to run `mkdir x` with Bash, and it stops at a permission prompt. The page raises a notification while it is hidden or unfocused and `ledung.notify` is `1` (what the Settings switch writes); the Notification's `show` event says the system took it. If the real banner can't be clicked, `dispatchEvent(new Event('click'))` on that Notification object runs the page's own click handler, which is what the app gets from a real click. Windows won't bring the window to the front for that event, and on a locked Mac no window takes focus.
- **A throwaway desktop app:** make a real one in the throwaway data folder from `npm run pack`'s output, with the same `ensureApp` (`src/platform/desktop-app.ts`) that `ledung` calls. On macOS the made app shares the bundle id `org.ledung.app` with the person's own app, so `open` could reach the real one. (`open` on the running app stands in for a Dock click: macOS sends a reopen, which Electron gives as `activate`.) Give the copy its own id first: `plutil -replace CFBundleIdentifier`, then an ad hoc `codesign --force --deep -s -`, as the make does. On Windows, have the app write its shortcut into the test folder with `Ledung.exe --ledung-write-shortcut=<file>` rather than into the Start menu, and open that `.lnk`, which is what a Start-menu click does. The copy shares the app id, so the taskbar groups it with the real app: read the names there, don't hover.
- **The macOS removable-volume prompt:** an app made or re-signed on an external drive makes macOS ask "would like to access files on a removable volume" on the person's screen before Chromium starts, and the window never shows. Don't answer the prompt. End that process and start the app directly, or make the app on the internal disk when the step needs a LaunchServices start.
- **Out of reach, so say it is:** a real banner, and a click on it, when the screen is locked or Do Not Disturb holds banners back (on Windows, `ToastNotificationManager.History` still shows the notification arrived). Also out of reach: the window taking focus from a real click, notification permission in System Settings, the person's real data and real Ledung, a phone, a physical key, two physical computers, and a hand on a real trackpad. Write these down as the person's steps to try, with what they should see.

## Commands

| Command | What it does |
|---|---|
| `npm run check` | Type check (core and page) and all tests. Run before every commit. |
| `npm run build` | Builds the page into `web/dist`. |
| `npm run release` | Check, build, copy to a new release folder and point the launcher at it. |
| `npm run pack` | Builds the npm package into `dist/ledung-<version>.tgz` (plain JavaScript). Never `npm publish` or `npm dist-tag` by hand: publishing goes through the two commands below. |
| `npm run publish:dev` | Publishes the next dev build (X.Y) to npm's `dev` tag, never `latest`, from a clean `main` that is `origin/main`. The manager may run it after merges (issue #461); `-- --dry-run` checks, builds and packs without publishing. |
| `npm run publish:public -- --confirm <version>` | Publishes the next public release (X) to `latest`. **The owners' word only** (Martin or FFBuddha, both publishers on npm), version included; no session runs it otherwise. |
| `npm start` | Runs Ledung from this folder (development only; use a throwaway config and data folder). |

CI runs on the public repository `Fluffy-Fluffy-and-Bouncy/ledung` (Martin, 2026-10-29, question #487; it had run by hand only on the private one, question #433): Windows on every PR update and push to `main`, macOS weekly and by hand, nothing for docs-only or site-only changes. CI is the last net, not the first: `npm run check` before every push stays the local gate. The pre-push hook (`.githooks/pre-push`, switched on by `npm install`) runs it and stops a failing push; `git push --no-verify` is the owner's call, never a session's.

## Code

- **TypeScript run directly by Node 24** (type stripping), no build step for the core: only erasable syntax (no enums, no parameter properties), and relative imports end in `.ts`.
- Follow the cross-platform rules in [docs/development.md](docs/development.md#cross-platform-rules): paths through `path`, user data through `src/platform/paths.ts`, everything about processes inside the runners and the host.
- Tests use `node:test` (`test/*.test.ts`). Security rules (`test/server-security.test.ts`), file access (`test/files.test.ts`) and the host (`test/host.test.ts`) are covered; keep them that way when changing those parts.
- Comments explain why, briefly, and point to the finding or decision behind a rule (for example "spike finding 2").
- Database changes are new entries in `MIGRATIONS` (`src/store/database.ts`); never edit an existing one.

## Rules that exist for a reason

- **Never offer "bypass permissions".** Production, personal-data and similar sensitive actions must always be able to reach the person using Ledung (brief section 5).
- **Sessions must not inherit `LEDUNG_*` settings** (`sessionEnv` in `src/runners/runner.ts`); otherwise a Ledung started inside a session uses the real config and data.
- **The page and API stay locked down:** Host check, sign-in cookie, Origin check on changes and the live connection, no embedding. The local network is opened only through the config (`"lan"`, `"lanSignIn"`).
- **Files are shown read-only and only from inside the session's project folder** (`src/sessions/files.ts`).
- **The session host stays small and changes rarely:** a running session keeps the host it started with.
